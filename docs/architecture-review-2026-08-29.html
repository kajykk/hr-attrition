#1 风险预测管线 — 从上帝服务到可插拔 Pipeline

Strong — 立即做
Files: app/services/risk_service.py (474) · app/ml/fusion_engine.py · app/ml/shap_explainer.py · app/api/v1/risk.py · app/core/redis.py · app/api/v1/ws.py
Problem

RiskService.predict 串行做 9 件事：kill-switch → 读缓存 → 查员工 → 构特征 → 调模型(to_thread) → 写表 → 调SHAP(to_thread) → 写缓存 → WS广播 → 建警。任何一步 mock 失败需同时桩 DB/Redis/模型/WS。全局 _fusion_engine/_shap_explainer 单例 + _reset_singletons() 测试后门是典型浅模块气味。SHAP 与缓存逻辑与预测强耦合，无法单独演进（例如想把 SHAP 改异步）。

Solution

抽 RiskPipeline 深模块：Pipeline[Stage]，Stage = LoadEmployee | BuildFeatures | Infer | Persist，其余为 Observer 插件：CacheStage、ShapEnrichment、WarningLink、WsNotify。引擎与解释器改为构造函数注入（不再是模块级全局），由 FastAPI 依赖提供单例。主流程只编排，不感知 Redis/WS。

Benefits

局部性：预测核心 4 步可在无 Redis/WS 的单元测试中 100% 覆盖；杠杆：新增“预测后写行为事件”只需加一个 Observer，不改主流程；AI 导航：后续问“风险分怎么算”只需看 Pipeline 一处。

#2 特征契约 — 单一真相源（SSOT）

Strong — 立即做
Files: app/ml/feature_engineering.py (训练侧 31 列定义) · app/ml/feature_provider.py (550 推理侧重建) · app/ml/models/feature_metadata.pkl · app/api/v1/risk.py
Problem

同一组 31 列特征在两处手写：STRUCTURED_FEATURE_COLUMNS 在两文件各一份常量，engineer_structured 与 build_structured_features 各自实现编码/派生（overtime/business_travel/dept one-hot 等）。虽有 assert_feature_contract() 运行时校验，但仍是“事后发现”而非“不可能错”。_FEATURE_DEFAULTS 与训练分布中位数分散两处，改一处易漏。

Solution

建 FeatureRegistry 深模块：单一 feature_spec.yaml / .py 声明 31 列的来源、类型、one-hot 映射、派生公式、缺省值。训练侧 engineer_* 与推理侧 build_* 均由此 spec 驱动生成（或至少共享同一组纯函数）。feature_metadata.pkl 改为由此 spec 构建时导出，而非手写常量对比。

Benefits

局部性：改特征只需改一处 spec，测试只需断言 spec；杠杆：新增“司龄分桶”派生特征时训练/推理自动对齐；消除漂移类线上事故。

#4 租户隔离 — 收敛为单一 AuthContext 深模块

Strong — 立即做
Files: app/core/tenant.py (ContextVar + middleware + deprecated require_tenant_header) · app/api/deps.py (get_current_user) · app/core/security.py · frontend/src/api/client.ts (已移除 X-Tenant-Id)
Problem

租户身份有三条路径：中间件 tenant_middleware（静默吞 JWTError）、依赖 get_current_user（严格校验）、已废弃的 require_tenant_header。ContextVar 在中间件与 WS 处理器两处设置，生命周期靠 finally clear。前端已不再发 X-Tenant-Id，但后端仍保留死代码，易误导新端点错误复用。

Solution

收敛为 AuthContext 深模块：单一 resolve_auth_context(request) -> AuthContext{tenant_id, user_id, role}，同时服务 HTTP 与 WS；中间件仅做 request.state.auth 注入，不再用 ContextVar。删除 require_tenant_header 与 get_tenant_id_from_context，所有业务层改由 Depends(require_auth) 显式获取，杜绝“忘记加依赖就越权”的隐式风险。

Benefits

局部性：租户越权测试只需测一处解析器；AI 导航：新端点不再纠结该用中间件还是依赖——只有一种写法。

#5 RAG 知识库 — 引入 FileStaging 端口，削薄 Service 门面

Worth exploring
Files: app/kb/service.py (402) · app/kb/parsers.py · app/kb/chunker.py · app/tasks/kb_indexing.py · app/core/redis.py (双客户端)
Problem

kb/service.py 同时做：扩展名校验、SHA 去重、DB 建记录、get_redis_binary 二进制缓存、Celery 入队、PII 扫描、切分、嵌入、pgvector 写入。Redis 有 get_redis（JSON）与 get_redis_binary（bytes）两套客户端，调用方需自行选对。Worker 与 API 进程的文件传递靠隐式 rag:file:{id} key 约定，无类型约束。

Solution

引入 FileStaging 端口（Port/Adapter）：staging.put(id, bytes) / get(id) / delete(id)，背后可为 Redis/Memory/S3。Service 门面拆为 IngestService(upload→stage→enqueue) 与 IndexingService(stage→parse→chunk→embed→store)，共享同一 Staging 端口。PII 扫描抽为独立 PiiScanner 可单测。

Benefits

本地测试可用 MemoryStaging，无需 Redis；未来切 S3 只换适配器；API 与 Worker 的隐式 key 约定变为显式接口。

#6 前端 Auth & 行为埋点 — 解耦三文件 token 与隐式 tracker

Worth exploring
Files: frontend/src/api/auth-keys.ts · frontend/src/api/client.ts (拦截器+刷新队列) · frontend/src/stores/auth.ts · frontend/src/utils/tracker.ts · frontend/src/router/index.ts · frontend/src/views/*.vue (748/703/634 行)
Problem

Token 生命周期分散三处：auth-keys.ts 管 localStorage、client.ts 管拦截器+refreshing 单例队列+Cookie 回退、auth.ts 管 Pinia。改一处易漏（曾出现“仅写 localStorage 导致 Pinia 状态过期”已修但结构仍脆）。tracker.ts 被 router/index.ts 直接静态导入，且用 void import(...) 动态导入做 visibility 监听，测试需桩 router。视图层 3 个 600+ 行大组件混有 API 调用与 UI 状态。

Solution

建 useAuthSession 组合式深模块：唯一持有 token/refresh/user，提供 login/logout/refresh 与 authHeader()，内部封装 Cookie 降级与队列。client.ts 仅消费它。tracker 改为插件 app.use(behaviorPlugin)，由插件监听 router hook，视图层只发领域事件。抽 useWarnings / useRisk composables 瘦身大视图。

Benefits

Token 刷新并发测试只需测一个 composable；埋点可整体 mock 掉；视图层行数减半，AI 改页面时无需读懂埋点细节。

#7 审计哈希链 — 抽离 HashChain 深模块，消除 FOR UPDATE 瓶颈

Speculative
Files: app/services/audit_service.py · app/models/audit_log.py · 调用方 app/api/v1/auth.py / warnings.py
Problem

每次 append_audit_log 都 SELECT ... FOR UPDATE ORDER BY created_at DESC LIMIT 1 取链尾，同一租户并发写入时串行化等待。哈希计算散落在 service 中，校验需全量扫表。当前量级尚可，但作为合规必选链，未来审计写入会随行为事件一起放大。

Solution

抽 HashChain 深模块：封装 append(payload) -> record 与 verify(tenant)，内部可演进为：链尾缓存于 Redis（audit:tail:{tenant}）+ DB 兜底，或批量聚合写入。调用方只传领域 payload，无需感知哈希细节。

Benefits

审计写入吞吐不再受行锁限制；校验可增量；AI 新增审计点时只需 hashChain.append(...) 一行。
